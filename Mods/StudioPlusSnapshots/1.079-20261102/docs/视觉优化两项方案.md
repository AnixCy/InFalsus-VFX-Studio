# 视觉优化两项方案：以 InFalsus Modded 1.07b 为本体依据

日期：2026-10-28。依据桌面 `ifstodolist.txt` 的“视觉优化”两项。本文件是分析和实施方案，尚未修改制谱器、本体或安装包。当前制谱器源码为 `studio_icon_work/Source`，已安装 DLL 的 SHA-256 为 `D73BDF55F376821658E1E7419403419917AB22B86298CA3C14F2F3F255A29E27`。本体输入为 `E:\RhythmGame\InFalsus\InFalsusModded1.07b`；所核查的可执行程序、资源及 DLL 哈希记录于 `visual_research_107b/evidence-hashes.json`。

## 一、背景看起来发灰、雾蒙蒙

### 问题和已经确认的原因

用户观察到背景不够清晰、像覆盖灰色蒙版；清单本身也要求先核查。这里的背景可能指用户选择的图片，也可能包括轨道后的动态中央图形及侧轨透过的区域，必须分开取样，不把三者混成一张图判断。

1. **已确认存在整条渲染链差异。** 1.07b 的 PlayerSettings `m_ActiveColorSpace = 0`（Gamma）；制谱器工程为 `m_ActiveColorSpace = 1`（Linear）。透明物件和其背后的颜色会在不同空间相混，所得画面可能不同；例如半透明层在两种空间混合后的亮度关系不一致。这是明确存在的技术差异，但单靠静态参数不能证明它就是用户所见灰蒙的唯一根因。
2. **已确认 Bloom 不是本体参数。** 本体 CoreScene 全局 Volume 的 Bloom 为 threshold 1.5、intensity 2.0、scatter 0.821、skipIterations 1、maxIterations 6，白色 tint、无污渍；ColorAdjustments 的曝光、对比度、色相、饱和度均为 0、滤色为白色，Tonemapping 模式字段为 0。制谱器 `NativeVisualPlugin.Post` 创建的全局 Bloom 为 threshold 1、默认 intensity 0.3、scatter 0.65，源码明确写了近似值；当前共享配置里的 `BloomIntensity` 也为 0.3。不同 Unity/URP 和色彩空间中的同名参数还需要用实际画面验证，不能仅把 0.3 直接调成 2 就宣称完成还原。
3. **未发现用户背景自身有固定灰色蒙版。** 编辑器 `StudioBackground` 创建相机前的背景四边形，背景着色器输出 `采样 RGB × _Brightness`、alpha 固定 1；默认亮度为 1，实际值可能被用户设置更改。它没有在这段 shader 中加灰色。然而背景仍会经过摄像机后处理，也可能被后续真实层覆盖；因此源码检查只能排除“该 shader 自身添加固定灰色”的假设，不能排除其他原因。
4. **本体对应背景有明确层次。** 1.07b 的 `GenericGameplayBackground` 将选中的背景材质交给 `Constrained2D`；`BackgroundObject` 为 3840×2160 参考尺寸，序列化颜色为白色。以本体 Mindscape2-Light 为例，材质 `_Alpha=1`、`_Color`/`_BaseColor` 为白、使用 `Unlit/StenciledUnlitSpriteOpaque`，并带模板 stencil；这是被核查的一种普通静态背景，不代表所有歌曲背景或运行时自定义设置都相同。背景上的动态 `BackgroundDiamond` 是独立图层，模糊用于本体该图形的合成，不等于整个背景必然被模糊。
5. 选中图片的实际亮度、图片自身像素、窗口与显示设置、图层相互覆盖仍会改变最终观感。当前没有用户对应画面、图片及两端匹配帧的像素取样，**因此“哪一层造成这次灰蒙”仍未证实**。该结论不会被写成“已确认有灰色蒙版”。

### 实施方案

1. 用 1.07b 的同一张背景素材和同一帧，构建可重复对照：等分辨率、16:9、色彩输出、固定 Brightness、同样的动态中央图形状态；记录用户背景图片原始像素、制谱器背景单独输出、叠加轨道后、后处理前后各阶段。对照纯黑/中灰/白及实际图中的中性灰和高饱和区域；全部数据在隔离测试目录产生。
2. 依次切换背景图、中央图形、侧轨、Bloom 和用户亮度，找到产生偏差的第一阶段。对透明边缘和无物件区域分别取样；核对图像采样的 sRGB 标记、RenderTexture 读写格式、Gamma/Linear 转换与合成次序。颜色不一致要分清是输入采样、透明混合还是后处理，不能用整体亮度或饱和度掩盖。
3. 在定位到差异后，按本体普通背景材质、白色/alpha、裁剪与层级、Gamma 合成及有效 Volume 参数实现等价的局部适配。若问题来自背景图片路径，则调整背景输出或对应的颜色转换；若来自侧轨或动态中央图形，则只修相应层的合成。不能无证据地删除本体的 BackgroundDiamond、将全部背景改为更亮，或直接把整个制谱器工程切换 Gamma。
4. 本体 Bloom 配置可作为目标配置的来源，先在隔离渲染中完整复现其参数及摄像机启用状态，并核查当前 URP 的行为和相关运行时覆盖；只在与 1.07b 的输出核对一致后接入。现有用户亮度、Bloom 开关和自定义值应保留，必要的默认值迁移不能覆盖用户明确设置。制谱器界面、谱面和选择行为不因颜色修复而变化。

### 验收

同图同条件下，分别对比无遮盖背景、半透明区域和最终画面，记录色值偏差、灰度、饱和度、裁切、边缘及 Bloom 高光；验证不同背景亮度、启停 Bloom、中央动态效果、侧轨和窗口比例。确认修复对关闭背景、缺失图片和已有自定义设置均正常。用修复前后同条件图和阶段采样说明实际造成灰蒙的层；没有找到能复现的灰蒙差异时，应如实记录，而不是引入猜测性改动。

## 二、Tap 看起来偏扁、发暗

### 本体逻辑与已确认差异

1. **资源本身不是主要缺失。** 1.07b 的 `note01` 网格与当前副本安装的 `Assets/Meshes/note01.mesh` 对照：20 个顶点的 XYZ 与 UV 最大差均为 0，索引数为 60。网格本体包中顶点范围约 X `[-0.1925, 0.1925]`、Y `[-0.18, 0]`、Z `[0, 0.0171163]`。已对照的是网格和 UV，材质贴图内容与运行时采样仍需进一步逐项校验。
2. **偏扁的明确代码原因：导入本体模型之后又套用了制谱器自定义尺寸。** `NativeVisualPlugin.cs` 的 `Tap` 将网格 Y 归一化到固定 `Profile.tapDepth`（当前默认 0.48），并把网格 Z 厚度固定乘以 2；横向由 `FloorBound` 和 `tapWidthRatio=0.94` 重算。播放优化 `PreviewTapMeshes.cs` 使用同一套固定缩放。因而模型虽是本体模型，实际纵深、厚度及随距离的变化并非直接沿用本体。
3. **1.07b 确有随距离改变 Tap 纵向比例的逻辑。** `Track._gBA`（当前二进制 RVA 0x677a70）计算音符与判定位置的相对视觉距离，再除以轨道距离得到比例 `q`；中央 Tap 分支设置实例局部 scale：X 为物件宽度乘 prefab 的 X，Y 为 prefab Y 加 `2q`，Z 使用 prefab Z；另有侧轨分支，不能把中央处理简单套给侧轨。中央 prefab 的序列化 scale 为 `(1,1,1)`、根旋转约为 X -90°，并引用 `note01`。因此在该分支下根部纵向因子是 `1 + 2q`，随距离增大，不是固定 0.48。1.07b 当前修改版在该方法入口有非官方 `hidegroup` 钩子；无隐藏时该钩子恢复寄存器并回到原方法，核查结果要按目标壳子的实际分支解释。
4. 制谱器与本体舞台单位和投影不同，不能把本体绝对数字直接当成编辑器单位。1.07b 的本体中央轨道半宽约 0.8，而制谱器默认中央半宽 2；默认视角也是经校准的独立参数。现有隔离投影研究给出等效 16:9 透视示例 FOV 约 51.945°、俯角 24.33°，与编辑器默认 50°、23.652°不同；它是投影推导，不是本体实机画面验收，也不应因此自动覆盖用户的相机配置。
5. **发暗有一个已确认的显示状态原因。** 编辑器选中 Tap 时，`DimSelected` 会将材质适用颜色的 RGB 乘 0.55，以突出橙色选择轮廓；取消选中时恢复。若比较的是选中 Tap，这一变暗是编辑器交互效果，与背景无关。对未选中 Tap，当前没有同帧像素证据证明具体是哪一项导致暗，不能把选中变暗、背景、色彩空间和 Bloom 一概视为同一原因。
6. 1.07b 中央单宽及多宽材质 `matid_notesingle` / `matid_notespan` 均采用 `Universal Render Pipeline/Unlit`，默认 `_BaseColor` 和 `_Color` 为白、透明队列 3001、`_SrcBlend=5`、`_DstBlend=10`、`_ZWrite=0`。`TapNote._ybA` 修改材质颜色的 alpha，保留 RGB；轨道逻辑按距离计算淡出 alpha。用户背景可以通过透明像素和淡出影响观感，但不能解释不透明 Tap 内部颜色的全部偏差。Gamma/Linear 合成及两端不同 Bloom 也是待分离验证的明确渲染差异。

### 实施方案

1. 从 1.07b 的中央单宽、多宽及两侧 prefab 开始，沿 Transform 父子链还原 mesh 的坐标方向、旋转、缩放、lane 方向与材质；以相机/判定线相对位置、可见轨道宽度建立明确的单位转换。计算 `q` 时使用本体对应的相对视觉距离及轨道长度，核对正负滚速、到达判定线和裁切边界。以本体目标分支为准，不能把 `0.48` 换成另一个目测常数。
2. 在 `NativeVisualPlugin.cs` 的普通 Tap 路径中按本体动态比例还原顶点，保留谱面时间锚点和轨道对齐；在 `PreviewTapMeshes.cs` 的播放缓存路径同步实现。动态比例发生变化时，缓存不能只更新平移而复用旧形状；应根据比例更新 transform 或重建必要顶点，并使形状缓存键、视锥剔除和近远裁切范围反映新的实际外形。
3. 保持可视 Tap 与拾取、框选及橙色描边一致。当前本体外观是由原 GroundCap 绘制结果替换，原四边形仍参与拾取；动态外形扩大后，必须检查可见部分与实际命中是否产生明显错位，并以渲染范围和编辑器现有稳定 SourceId 为基础做最小适配。不得修改谱面事件、轨道编号、时间或撤销规则。
4. 颜色按“未选中／选中”分开对照：先验证本体单宽、多宽、左右侧对应贴图、UV、透明度、着色器、混合因子和排序，再用相同背景及 Bloom 条件测试 Gamma/Linear 差异。只有定位到未选中 Tap 的实际颜色偏差后，才给 Tap 材质或混合路径做与本体等价的局部适配；若差异来自上一项的公共后处理，优先修公共原因。不能直接调高白色系数或画一层高亮替代本体材质。
5. 选中变暗与橙色轮廓是已有编辑交互，保留其选中/取消恢复逻辑；比较本体外观时使用未选中状态。若选中后用户仍认为过暗，可单独讨论编辑态样式，不应误当成本体 Tap 的默认材质颜色。

### 验收

在同一 16:9 视口、等价相机和单位映射下，对照 1.07b 近、中、远三处的 Tap：单宽、多宽、左右侧各一组；验证 q、宽度、投影外轮廓、前后边缘、厚度、UV 和 alpha。覆盖网格模式、自由模式、静止、播放、拖动、变速、裁切边缘、选中/取消和重叠 Tap。逐帧比较普通绘制与播放缓存，确保外观一致且无闪动；检查命中区域、选择轮廓、撤销与源谱字节。

## 建议执行顺序

先进行两端同条件基线取样，定位背景灰蒙的实际层；再恢复该层本体渲染及必要的后处理。随后按本体动态距离公式和 prefab 层级修正 Tap 几何与播放缓存，最后在公共背景和后处理已确定的条件下处理未选中 Tap 的颜色。先做隔离验证再按用户指定范围安装；本轮仅交付本方案。
