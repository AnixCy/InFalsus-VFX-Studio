# 游玩模式延迟重写方案

状态：设计方案，2026-11-02。尚未实装，未修改源码或副本。
目标：重写游玩模式的音频输出、时钟、输入计时和音效调度，降低实际敲击音延迟及抖动，使延迟校准具有明确、稳定的含义。

## 一、已经确认的问题

| 当前实现 | 问题及影响 | 重写方向 |
| --- | --- | --- |
| `GameplaySession.Tick` 从 `PlaybackPresentationClock.TimeFor` 取判定时间 | 判定受画面平滑、每帧缓存影响；同帧不同时间发生的输入被压成同一个时间 | 直接从独立音频时钟换算输入事件时间 |
| `GameplayInputSampler.Sample` 每帧读取状态，LastPress/LastRelease 写入帧时间 | 丢失帧内先后与间隔；短按在一帧内完成时可能只剩最终状态 | 保存按下、松开和鼠标事件及原始时间戳 |
| `ReactiveAttacks.Shot` 只有 Sample/Gain/Position | 不知道输入或请求发生时间，所有入队攻击音从下一可写块的第 0 采样起播 | 带事件标识和时间的统一音效命令 |
| 攻击音走 ReactiveAttacks；持续音另走 PcmMixState 与 audioNow | 两套起点、状态与时基；视觉桥同时负责混音，维护时容易再次错配 | 独立 GameplayAudioScheduler，音效共享设备与 DSP 帧时基 |
| 音乐和音效依赖 Unity 音频配置与 AudioSource | 缓冲不可直接等同入耳延迟；现有代码没有足够测量来证明固定补偿值 | 游玩模式改用独立 FMOD 后端，读取实际配置并记录延迟阶段 |
| 用户延迟同时参与画面和判定，却不改变物理音效响应 | 校准会混入设备延迟与个人依据；不同听觉参照可能得到不同最佳值 | 保留明确的主偏移，降低物理音效延迟，必要时单独微调画面 |

注意：`PlayScheduled` 前预留的 80 ms 是起播准备时间，不能直接算成每次敲击音的额外延迟。也不能把 `bufferLength × bufferCount / sampleRate` 当成设备输出延迟的实测值。

## 二、总架构：重写游玩音频，沿用编辑和导出

主方案采用 **FMOD Core + 独立游玩传输与时钟**，与本体的处理方向一致。音乐、Tap/Flick 攻击音和 Hold/Sky 持续音全部进入同一个 FMOD System。FMOD Core x64 运行库与最小绑定是本次方案明确新增的依赖，固定匹配版本；不依赖安装本体，也不把本体私有桥接 DLL 当成制谱器运行依赖。

编辑预览、正式/非正式预览、自动剪歌、频谱分析和离线视频混音继续使用现有路径。新后端只在进入游玩时取得播放所有权；退出时释放所有权并恢复原来的编辑位置与音量。

建议拆分：

| 新模块 | 责任 |
| --- | --- |
| `GameplayAudioHost` | 会话生命周期、资源预热、设备、唯一音频后端 |
| `FmodGameplayBackend` | FMOD 初始化、分组、混音时钟、播放与采样排程 |
| `GameplayTransport` | 起播、暂停、定位、速率、结束；谱面时间与音频位置换算 |
| `GameplayClockBridge` | DSP 帧与 Stopwatch 高精度时间互换，发布带代次的时钟快照 |
| `GameplayInputTimeline` | 保存带时间戳的按下/松开/鼠标输入，建立输入历史 |
| `GameplayJudgeRunner` | 将事件时间交给现有判定规则，协调连续音符与最终结算 |
| `GameplayAudioScheduler` | 攻击音与持续音统一命令、时刻、去重和音量处理 |
| `GameplayPresentationAdapter` | 向既有轨道、HUD 等提供显示时间与状态 |
| `GameplayAudioDiagnostics` | 记录时钟残差、输入处理耗时、音效排程延迟和丢事件计数 |

线程分工：主线程负责 Unity 输入接收、判定及界面；音频控制线程负责音频命令与传输状态；FMOD 混音线程负责实时输出和时钟快照；解码/保调处理在线程外提前准备。将音频移到后台不能消除 Unity 输入到达主线程之前的等待，此项需单独计量。

## 三、统一计时模型

全程以输出设备 DSP **帧**计数为公共单位；一帧包含全部声道的同一时刻采样，不能把立体声样本总数当帧数。所有 ChannelGroup 使用同一父时钟和固定 pitch=1，避免混用通道局部时钟。

设：

- `Fs`：实际输出采样率。
- `D0`：当前播放段开始的 DSP 帧。
- `C0`：该播放段起点的谱面毫秒。
- `r`：播放速率，保留现有 0.25～2 的范围与保调行为。
- `O`：谱面工程音频偏移，保留原语义 `audioTime = chartTime + O`。
- `G`：用户现有“游玩延迟”，单位为谱面毫秒。
- `V`：可选高级项“画面微调”，单位同为谱面毫秒。

正常播放段的公式：

```text
RawChart(D) = C0 + 1000 × r × (D - D0) / Fs
SourceAudio(D) = RawChart(D) + O
JudgeTime(D) = RawChart(D) - G
DisplayTime(D) = JudgeTime(D) - V
```

`G` 保留默认 0、范围 -1000～1000 ms、正值延后画面和判定的语义；速率不为 1 时，其现实时间偏移为 G/r 毫秒，在说明与检查中明确。若将来要增加“按现实毫秒校准”的模式，必须单独设计，不能悄悄改变已有值含义。

`V` 默认 0，可放到游玩音频高级设置，建议范围 -200～200 ms；只移动画面，不移动判定、音乐或敲击音。它用于分离视觉感受，不自动补偿设备，也不随音效开关改变。

`G` 和 `O` 不合并；不因启用打击音自动增减 G，不自动扣掉 85/100 ms，不为开/关打击音各偷偷保存一个最佳值。现有 G 配置先保留；后端延迟变化后需要重新校准，旧值可能不再适合。

启动前等待和暂停使用状态机，不能把 JudgeTime 强行截到 EntryTime，否则正偏移会在开头形成静止平台。内部允许负的相对时间；界面若需要可只限制数字显示，不能限制判定时钟。

## 四、音频时钟桥

1. FMOD 混音侧发布 `(generation, dspFrame, stopwatchTicks, sampleRate, blockFrames)` 快照。先核定回调读到的是块起点还是块终点，统一换算后再发布，防止固定差一块。
2. 用 Stopwatch 频率进行块间外推。输入与显示从同一时钟映射取值，去掉游玩判定中的一秒低通修正、`Time.frameCount` 缓存及允许领先 50 ms 的逻辑。
3. Unity 输入事件时间与 `realtimeSinceStartup` 同源，但与 Stopwatch 的零点不能假定相同。用前后夹取的成对时间建立映射，丢弃采集耗时过大的样本；保留小段历史快照以查询过去的输入时间。
4. 连续播放段要求单调；暂停、定位、速率或设备变化建立新 generation，清理旧命令。不能用全局 `Math.Max(oldTime,newTime)` 隐藏定位或失步。
5. 采样率/缓冲改变、长时间断流或时钟残差异常时进入恢复流程。禁止时钟无界外推，也不在回调里重建音频设备。
6. DSP 时钟仍是音频引擎的时间基准。未测量的驱动/设备延迟不被冒充为已补偿的“耳朵时间”；用户 G 仍可包含这部分校准。

## 五、缓冲与播放处理

- 初始请求与本体一致的 **256 帧 × 3 块**；提供 128、256、512、1024 帧的高级选项，默认 256。64 帧先不作为默认支持项，待必要稳定性检查后再决定。
- 采样率优先匹配输出设备；实际值以 FMOD 查询结果为准。48 kHz 下 256 帧约 5.33 ms、三块容量约 16 ms，此数字只用于诊断。
- 默认使用可共享设备的系统输出，记录实际输出模式。设备或缓冲变更在游玩开始前生效，不在敲击过程中反复重建设备。
- 进入游玩前加载音乐与全部所需攻击音、持续音。声音开关关闭也保留就绪的音效资源，不因开启开关临时启动第二套设备。
- 音乐先创建暂停通道，选定 D0 后按父组 DSP 时钟排程起播。准备提前量只属于开场，不附加到每个攻击音。
- 保调继续使用当前 WSOLA 算法，通过新音乐 PCM 供应器供给 FMOD；1 倍速直接使用原 PCM，不额外经过保调处理。解码和 WSOLA 提前计算，回调只取现成数据；提前准备的数据量不等同给攻击音增加相同长度的输出排队。
- 主线程先把 Unity 音乐与旧游玩音效停下，新后端获得所有权后才开声。退出时反向恢复，防止两条音乐同时播放。
- 初始化失败明确中止本次游玩并恢复编辑现场；不静默切回旧音频路径后继续使用相同校准值。

## 六、重写输入计时与判定接入

订阅当前已有 Input System 的事件流，记录事件时间、顺序号、设备、轨道、按下/松开、鼠标位置/位移；从完整状态和增量状态事件提取边沿，不重复把同一次按键从旧 Input.GetKey 和新系统各读一遍。保持当前鼠标灵敏度与系统处理后的位移语义，排除程序回中产生的鼠标事件。

先收齐本次输入更新的事件，按时间和顺序号处理，再推进该帧末的连续判定。Tap/Hold 头部使用按下事件的 JudgeTime；Hold 尾部使用真实松开时间；Sky 离域/回域与 Flick 穿越使用鼠标轨迹时间，不再把整帧轨迹当成一个瞬时位置。

不能简单地对旧 `Engine.Step` 调用多次：它会清空 Results、提交持续音符状态，迟到输入还可能早于 previousNow。需要把调用接口拆成输入提交、连续时间推进、结果提交三部分，保留原有判定窗口、优先级、Sky 紫条/红条规则和 noinput/hidegroup 过滤。

建议保留至少 2 秒的输入历史。主时间单调推进，头部判定直接使用事件时间；短暂迟到的输入回评尚未最终提交的候选。Miss 等不可逆结果可延迟提交一个有限的输入交付宽限期，默认按近期两个输入更新间隔计算、上限 100 ms；它只推迟宣告 Miss，不扩大“输入发生时间”的合法判定窗口，不推迟成功敲击音。超出可恢复历史的迟到事件必须记为诊断异常，不把它改写成当前时刻。

不要把判定逻辑搬到 FMOD 音频回调。主线程的判定结果通过一次性、带编号的提交包发给音频线程与显示层；旧每帧清空结果列表不能使同一事件被重复播放或漏播。

## 七、统一攻击音与持续音

### 攻击音

新命令至少包含：`generation、sequence、sourceId、kind、inputDspFrame、requestTicks、targetDspFrame、gain`。

有效输入经现有判定规则确认后立刻生成命令，不等 HUD 动画或下一次视觉 Tick；预加载 FMOD Sound，避免临时创建 Unity AudioSource。目标是在当前最早可写的 DSP 时刻播放；能精确排程时使用块内采样位置。

输入事件很可能是在目标混音块已经提交后才被主线程处理，因此必须有明确迟到策略：从最早可写时刻完整播放攻击音，保留第一个采样，不为追赶过去的时间截掉音头；同时记录这次排程晚了多久。不得承诺靠时间戳就能回写已输出的声音，也不按未来音符时间提前播放来伪造低延迟。

不默认增加固定的一帧或一块等待。音效目标样本和判定事件时间分别保存：前者受设备可写进度约束，后者不能被音效排程反过来修改。

### 持续音

Hold/Sky 改为同一调度器下的开始、更新、结束命令，命令含 DSP 时刻与 generation，循环相位按同一音频时间轴计算。保持 Hold 头音和 Sky 首段策略的现有选项。

正常松开使用约 2～5 ms 的短淡出抑制爆音；淡出只是采样包络，不是判定宽限，也不能用于掩盖几十毫秒的起播延迟。Sky 出域、红条冷却、重新捕获以现有判定状态转移为准。

### 开关与音量

HitSounds 只静音/停止音效分组并取消该组待播命令。音乐通道、设备、D0、G、时钟映射与判定状态都保持连续；重新开启时不补播关闭期间的历史攻击音，只恢复当前仍有效的持续状态。关闭音效后可使该组不进行无用混音，但公共时钟桥继续运行。

## 八、与旧代码的具体替换关系

| 现有位置 | 实施动作 |
| --- | --- |
| `GameplayPresentationBridge.ReactiveAttacks`、WarmSound、TriggerShot、PcmMixState 游玩发布、MixAttacks | 从游玩链路删除，由新音频 Host/Scheduler 接管；保留视觉反馈与 HUD 绘制 |
| `GameplaySession.Enter/Tick/Exit` 的 Transport.Play、音量覆盖、按帧取 Now | 重写生命周期，使用新传输、输入时间线和判定 Runner |

| `PlaybackPresentationClock` 中游玩 Latency 分支 | 删除，游玩显示直接读新 PresentationAdapter；编辑预览平滑器继续原用途 |
| `GameplaySession.Install` 中 OnAudioFilterRead 的 MixAttacks 补丁 | 删除，游玩不再接管旧编辑音效回调 |

| `StudioTransport`、StudioKeySounds、PcmKeySoundMixer | 保留编辑/预览/导出用途，不将新游玩偏移写入这些通用对象 |

旧实现保留在开发备份/版本记录中便于整套回退；正式运行链路不保留多个可同时工作的游玩音频后端。有限的接入补丁集中在会话所有权与显示适配，不继续在多处叠加延迟修正常量。

## 九、实施顺序

1. 新建后端与时钟模块，完成音乐、起播/暂停/定位、设备配置和基础诊断；确认与原编辑播放互斥。
2. 接入事件输入、时间换算与判定 Runner，消除平滑时钟和按帧重写输入时间；保留既有判定结果。
3. 接入攻击音、持续音及声音开关；删除旧游玩混音回调路径。
4. 接入全部轨道/HUD 时间，处理开场、末尾、失焦、重入、设备变化，保留保调播放。
5. 做下列必要验证后整体安装副本。仅方案阶段不安装、不打包。

## 十、必要验证与验收标准

1. **确定性计时检查。** 同一组带时间戳输入在 30/60/144 FPS 下，成功/失败、等级和误差应相同，毫秒换算数值误差小于 0.1 ms；覆盖同帧按下再松开、鼠标离域后回域，以及少量迟到输入。声音开关不改变同一输入轨迹的判定结果。
2. **采样排程检查。** 用已知 PCM 脉冲确认起播、音头完整性、声道/帧计数、暂停重入和 generation 隔离。合成的未来定时事件可核对到 1 个输出采样；此精度不能等同真实按键到入耳耗时。
3. **实际输出必要检查。** 记录输入事件时间、主线程接收、音效提交、首次混入四个阶段。正常负载下以“提交到首次混入 P95 不超过两个实际 DSP 块加 2 ms”为工程目标，测不到就报告原因，不以编译结果代替它。另记录事件接收到提交的帧等待与抖动，不藏入总偏移。
4. **传输与隔离检查。** 覆盖 O/G 正负值、0.5/1/2 倍速、从中途开始、音乐提前结束、失焦退出、重新进入；编辑预览和视频导出不受游玩设置影响。连续切音效开关不得重启音乐或使公共时钟跳变。
5. **一次集中听感验收。** 由用户用同一谱面与同一有线设备对比开关敲击音。若仍有明显差距，根据阶段记录区分实际输出、输入到达和个人听觉参照；不先补固定 100 ms。可取得回环音频时作为输出证据，但软件回环不代表完整的耳机/蓝牙声学延迟。

不能预先保证所有设备的总入耳延迟、两种听觉参照下的最佳校准完全相同，或绝对不需要重新校准。本次要做到的是：实际输出尽量短且稳定、每段延迟可追踪、判定不受画面平滑影响、用户设置含义不随声音开关变化。
