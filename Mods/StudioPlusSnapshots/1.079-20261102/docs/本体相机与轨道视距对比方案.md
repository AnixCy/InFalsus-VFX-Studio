# 本体 1.07b 与制谱器默认相机：对比及调整方案

核对日期：2026-10-28。本体：E:\RhythmGame\InFalsus\InFalsusModded1.07b。编辑器：当前 InFalsus Studio+ 副本，核心 1.0.10，当前插件源码 studio_icon_work/Source。

## 结论

相机本身可以通过现有设置还原本体在 16:9 下的投影，不必修改制谱器代码。推荐先只应用下方四项相机参数，保留其余参数；不建议为这次调整直接替换所有用户的默认配置。

不过，制谱器默认画面原本已很接近本体：旧参数来自截图拟合，尤其判定线位置几乎一致。真正还存在的差异包括轨道沿纵深拉长、侧轨坡度和原模型细节重映射。这些不是继续调相机就能完全消除的。

本轮只输出方案和可导入 JSON，没有更新个人配置、安装副本或压缩包。

## 本体真实参数与换算依据

本轮从新本体的 Addressables 场景资源重新读取，未套用旧版研究记录。

- CoreScene / CameraPerspective：Transform 1953，位置 (0,0,-10)，旋转为单位四元数。Camera 3847 的 projectionMatrixMode=2，启用物理投影；SensorSize=(36,24)，焦距 20.7846107483，LensShift=(0,0)，GateFitMode=2，即 Horizontal。
- 资源中 field of view=60.0000038° 是传感器对应值。横向适配到 16:9 后，有效垂直视角是 **51.9450607°**，不能把 60° 直接填进编辑器。
- GameScene / GameCamera：Transform 2398。名字虽叫 Camera，实际是舞台父节点，位置 (0,0,-7.0200004578)，四元数 (-0.2107276618,0,0,0.9775448442)，等效绕 X 轴 -24.33°。真正 Camera 不在这里。
- 制谱器把舞台放平，改为相机绕 X 轴 +24.33°；两种方式可数学等价。
- 本体中央四轨范围约 ±0.8，制谱器默认 ±2，使用统一长度倍率 k=2.5。本体地面逻辑判定位置以舞台局部 z=-1.5 为基准，制谱器为 z=0。细节美术对象存在微小偏移，不拿美术描边端点替代逻辑轨道宽度。

换算：设舞台旋转 R=Rx(-24.33°)，舞台原点 T=(0,0,-7.0200004578)，实际相机 C=(0,0,-10)，判定基点 J=(0,0,-1.5)，则编辑器相机位置为 `2.5 × (R⁻¹(C−T)−J)`，结果约 `(0,3.069336,-3.038347)`。

有效垂直视角：`2 × atan(36 / (2 × 20.7846107483 × (16/9)))`，约 51.94506°。

CoreScene.Update 的本地反汇编也确认了屏幕比例与 16:9 相机 rect 的适配；场景中保存的 rect=(0,0.125,1,0.75) 是某个屏幕比例下的序列化状态，不能固定照抄到 16:9 窗口。该调用链中没有发现把上述相机改为另一个 FOV 的直接 setter。本方案针对默认游戏视图，不覆盖额外动画/演出或未来模组改写。

Unity 对物理投影与 GateFit 的定义核对自官方源码：
https://github.com/Unity-Technologies/UnityCsReference/blob/master/Runtime/Export/Camera/Camera.bindings.cs

## 相机参数不能完全解决的部分

### 1. 纵向视距：轨道被额外拉长

本体 TRACK_FLOOR_END 与 JUDGEMENT_LINE 两个标记的局部纵深差为 20.1818113327；按中央宽度的统一倍率 2.5，等效制谱器距离为 **50.454528**。

制谱器默认 `stageFar=65`。当前 NativeVisualTrack.cs 更明确使用 `far/20.181811` 来重映射轨道 Z，而横向是另一套宽度映射。这使逻辑轨道终点距离比统一还原比例长约 **28.83%**。这里说的是判定点到轨道终点标记/渐隐参考的距离，不是原始网格最远顶点，也不是相机远裁面；原始网格本就可能越过终点标记。

按换算后相机，z=65 的投影 Y≈97.815，z=50.454528 的 Y≈113.459，相差约 15.64 px。这解释了只改四项相机后，轨道尽头仍不完全一样。

若进一步要求还原：

1. 增加显式的“本体 1.07b 视图”预设，将 stageFar 设为 50.454528，并沿同一倍率核对轨道主体、侧面三角形、远端背景参照和渐隐参数。
2. 核对 stageFar 涉及的 NoteRenderer、网格、拾取、预览剔除、背景放置，保证显示与可编辑范围一致；不能仅缩短地面网格。
3. 不自动更改视速或 `unitsPerSecondAtSpeedOne=15`。可提前看到多少秒还取决于滚速和谱面 timing/track；相机距离、轨道长度、时间提前量必须分开。
4. 当前 JSON 加载器能够载入 stageFar，但相机面板没有该滑杆，共享 CameraState 也没有持久化它。只提供一个含 stageFar 的 JSON，会导致它不随现有相机记忆完整恢复。因此本次正式推荐文件不含 stageFar；完整预设实现时应加入版本化保存与旧配置兼容。
5. 保留“原图像校准”预设和已有自定义参数，不启动时强制覆盖。避免把本体 farClip=1000 生硬复制给制谱器：当前相机 farClip=120 已能覆盖舞台，调大它不会消除 stageFar=65 的网格/作者范围裁切。

### 2. 左右侧轨坡度

本体侧轨模型的旋转包含 45° 斜坡；制谱器按 `atan(sideRise/sideRun)` 构造坡面，默认值 0.7716634/0.8252873 得到 **43.07679°**。这是真实几何差异，调整相机俯角会连中央轨道一起变化，无法只纠正侧轨。

现有相机设置页包含“侧轨高度/侧轨横距”，原则上不用重写程序就能调坡度。单纯 45° 要求两者相等；从原侧轨网格横截面约 0.45 的斜向宽度换算，两方向理想跨度各约 0.795495。但原模型还有安装偏移、接缝和判定描边，当前插件又把原始 X 区间归一化到 StageSpace，因此 **0.795495/0.795495 只能作为后续几何对照的候选，不能宣称整条侧轨已经精确复刻**。这次先保留两项默认值。

若实施完整几何还原，先把原模型各父节点变换应用到判定截面，再检查中央/侧轨交界、侧轨音符、拾取面、辅助线和光效。共同使用同一几何规则，不通过独立挪动贴图补视觉接缝。空域高度同样涉及逻辑平面和美术锚点，本次不随相机一并改动。

## 建议执行顺序与验收

1. 先手动导入四项相机 JSON，不改 DLL；用同一有效 16:9 视口观察判定线、中央轨道中段和远端。回退文件已提供。
2. 如需全部轨道几何一致，再实施可选本体预设：统一纵深倍率、侧轨断面、远端渐隐，并补足参数持久化。
3. 比较相同谱面、相同时间点、同等实际滚动距离，使用暂停帧并隐藏编辑 UI；相机投影与材质/Bloom/背景色差分开验收。
4. 预设实现后检查 16:9、带黑边窗口、重启恢复、相机参数加载/回退、音符拾取、时间标签、十字线、段选线及侧轨 Hold/Flick；不修改 SPC 或音频偏移。
